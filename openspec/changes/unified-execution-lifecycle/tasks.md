## 6. Rework: execution and attachment ownership

- [x] 6.1 One attachment record, no execution copy. Claim streams record attachment facts only (registration, subject, metadata, session, standing, grant time); identity, birth, binding, observation, placement, signal, exit, completion and pane cleanup are recorded on the execution stream and read from there. The combined fact type is gone (`Recorded::Attachment`/`Execution`), `reduce` is split by stream, `read_claim` composes the execution, `sync_claim` and its call sites are deleted, and `write_attempt` records execution changes on the execution stream instead of projecting a copy. A claim transition validates against the execution record, so the guards that refused an ended process survive without a copy. Verified: library 577 (including `a_claim_reads_its_execution_instead_of_carrying_a_copy`), control-plane 178 (1 ignored), every other target green; fmt, strict Clippy (large variants boxed) and OpenSpec clean. The absence of the copy is enforced by construction — the field and its synchroniser no longer exist — rather than by a test that could pass on a re-synchronised copy. `context/lifecycle.md` records the decision. The record shape changed, so earlier alpha state is refused and cleared with `radar reset --hard`.
- [x] 6.2 Accepted launch metadata is applied at grant with named intent taking precedence. The precedence itself landed in S1 (the execution's recorded intent wins when it is not the default); this pass supplied the evidence and corrected nothing: `a_launch_that_names_no_intent_continues_the_session_s_metadata` launches description-only, no-intent and restated-intent executions through `create_with_intent` and enrols each with the same session, so it proves a session's metadata outlives the process that named it, that absent intent retains it, and that restated intent replaces it. Verified by mutation: with the continued-metadata fallback replaced by a default, the test fails reading empty metadata where the session's owner, run and label should be.
- [x] 6.3 Preserve the hook promise chain and serialize session boundary work per registration. Shutdown releases the exact claim; start sends registration/session and persists Radar's returned ID; heartbeats/release name it. Resolve reserved IDs instead of replacing them. Carry start reason as context, not a retry token. Remove client-minted authoritative IDs, generic previous-claim replacement and its Reserved skip, with no adapter or mandatory attempt subsystem. Verified: the hook wrapper returns its handler's promise, so `session_shutdown` does not return until the release answers (a held-open release keeps the boundary open; discarding the promise fails that test), the report names Radar's claim or none at all, a lost first reply recovers the attachment it already made (fails with the discovery branch disabled), a released claim cannot be reopened, a report for another session is refused without displacing the incumbent, a same-session reload reuses the attachment, and a different session releases the held one. Wire 19, because the presence report's claim identity moved to the daemon. Retain bounded existing transport-failure handling without silently abandoning queued releases or adding automatic intent retry.

## 7. Rework: independent reservation and grant

- [x] 7.1 One authority order over claim records. S1 removed the writable subject pointers; this pass fixed the order they are read in: `current_attachment` now resolves the claim that holds the subject, else the newest live claim, else the last recorded, so a reserved successor waits beside the grant instead of becoming the subject's attachment. Verified by mutation: `a_reserved_successor_does_not_become_the_subject_s_attachment` fails with the grant precedence removed (`live.or(last)`) and passes with it, and also asserts the reservation is recorded beside the grant (`reserved_claim`) rather than in place of it. The regression it caused was a real addressing defect, not test drift: cancelling a reserved successor was refused because resolution went through the subject's current attachment while the request named the successor's claim. `cancel_target` now resolves the execution from the claim the caller named, and a claim that is neither the subject's grant nor its reservation is refused with the same wording as before. Existing refusals for a stale or foreign claim are unchanged (`a_control_naming_a_stale_claim_signals_nothing`).
- [~] 7.2 Restart failure paths. Covered: `restart_stops_the_verified_lead_then_launches_one_resumed_successor` (the happy path through the real control plane) and `restart_refuses_before_any_signal_when_the_session_context_changes` (refusal before any signal). Added this pass: `an_undispatched_restart_reservation_restores_its_incumbent` now starts from a *granted* incumbent and asserts the grant survives the reservation's withdrawal — with `cancel_reservation` also releasing the predecessor the assertion reads `None` and fails. Still to verify explicitly: a stop that fails cancels only the reservation while the incumbent keeps running, and a successor that fails after the predecessor exited leaves the subject detached rather than restoring the exited grant.
- [x] 7.3 Shared claim release and registration finalisation. Session shutdown normally releases the exact claim; `record_completion` now records the authenticated supervisor's completion *and* establishes the execution end and settles its outstanding claims through `record_exit_locked`, so a completed execution holds nothing without waiting for a pane notification or a sweep. `record_exit` (the unlocked recorder) delegates to the same locked settlement instead of keeping a second copy, and verified fallback observations and failed-launch withdrawal still enter it. Completion keeps spontaneous-exit pane retention separate from explicit close. Verified: `supervisor_completion_ends_the_execution_and_releases_its_claim` (the claim reads `Reserved` without the settlement and `Released` with it; the established end and the first report's status survive a replay) and `a_completion_after_a_verified_exit_records_the_status_it_carries` (a late report adds the status without moving the established end or resurrecting the released claim). Full Rust gate green: 577 library, 178 control-plane (1 ignored), every other target passing; fmt and strict Clippy clean.
- [~] 7.4 Reservation mismatch at the shared attachment operation. Implemented: a reservation for the presented session's own subject that names another execution is settled (released) before the attachment is judged, so a restart or continuation that will never arrive neither blocks the session that returned nor holds the subject until its deadline; `a_reservation_that_can_never_arrive_is_settled_when_the_session_returns` fails with the settlement removed ("the session is already attached to another live process") and passes with it, and asserts the presented session continues its own subject and the reservation reads `Released`. A reservation for a subject the presented session does not own is still not cleared, because that reservation belongs to another execution. Open: the failed intent is not yet visible in the TUI — that needs the failure published as an observation record, which is 8.1's surface; until then the settlement is recorded only on the claim it ends. No automatic retry.
