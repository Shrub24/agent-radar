# Tasks

## 1. Container records, bindings and reads

- [x] 1.1 Define the container record: durable identity, kind (workspace, tab, pane slot), parent link, label, provenance (created by Radar, or observed) and a separate backend binding (backend name, serving instance, raw handle), stored bounded and owner-only.
      Status: implemented in `src/control_plane/containers.rs`; the record is committed to the durable log as a `ContainerCreated`/`ContainerObserved`/`ContainerRemoved` transition.
- [x] 1.2 Record containers on the paths that create them, so a created workspace, tab or pane is owned before it is reported, and a created agent pane also carries the spawn edge that binds its child.
      Status: implemented for the `mux.create` path: only the identity the request asked for is recorded, the parent resolves to a recorded container or stays absent, and the container is appended before the creation is reported. An agent container's child binding is unchanged and still travels through the spawn contract.
- [x] 1.3 Add bounded paginated container reads carrying per-source freshness and the binding as evidence: missing, replaced, ambiguous or handle-reused bindings stay visible and unresolved.
      Status: implemented as `topology.get.v1` and `topology.list.v1` (`Method::Registry`, no backend needed). Each record carries `observed_at` as freshness, `unresolved` as a source-labelled reason and the binding as evidence.
- [x] 1.4 Add reconciliation that reports observed drift (missing, foreign, changed handle, replaced serving instance) as source-labelled facts without rewriting identity, adopting a foreign handle or deleting a record.
      Status: implemented as `topology.reconcile.v1` (needs `mux.observe`): one bounded pass writes one `ContainerObserved` fact per recorded container, keeps every record, and dispatches nothing. It refuses when no inventory can be read rather than recording that everything is missing.

## 2. Creation

- [x] 2.1 Add workspace, tab and pane creation from an explicit request naming the parent container and the recipe (label, working directory, command, environment, backend options).
      Status: partial. `topology.create` creates a workspace, tab or pane with a label, resolves its parent against recorded containers only, records the container before the creation is reported, and answers with that container (a replay of the same request id answers with the same one). The launch half of the recipe — working directory, command, environment and backend options — is not accepted yet; it lands with the tracked launch, so a creation carrying a command and the reload that pairs with it stay open.
- [x] 2.2 Keep recipe values private: bounded owner-only storage, and no recipe value in any read, log, diagnostic or event payload.
      Status: nothing to store yet. The label is bounded and control-character-free at the wire boundary; a working directory, command or environment value is not accepted at all, and no creation value reaches an event payload.
- [x] 2.3 Create agent containers through the existing spawn contract, so the child still binds to its exact `agent_id` and the container records the pane slot it was launched into.
      Status: implemented. `spawn.create` records the pane it dispatched into, bound to the verified serving incarnation, before the edge and the launch are recorded; the child binding is unchanged.
- [ ] 2.4 Refuse or leave unresolved rather than record a container whose creation could not be confirmed, and never retry an uncertain creation under a new request ID.

## 3. Deletion

- [x] 3.1 Add container deletion as a durable operation with confirmation naming the exact container and the possible losses, a verified binding, and an outcome recorded before the caller is answered. `topology.delete` (`topology.delete.v1`, requiring `mux.close`) takes the container id and the client's frozen target, refuses into its record when the container is unknown, has no binding, or binds another place, and marks the container and its recorded subtree removed only after the runtime confirms the close.
- [x] 3.2 Refuse deletion that would end a live managed process, naming that process, and let the operator run the recorded stop-then-delete sequence, with pane removal and process exit reported separately. The refusal names each registered worker in the container's own subtree and the sequence to run; a live process is never signalled by a deletion, and the recorded note reports the close and the removals only.
- [x] 3.3 Refuse a reused handle under a different serving instance, and keep deletion from claiming any process exited or any assignment completed. The binding's verified serving incarnation is re-established before any dispatch; a container with no recorded incarnation is refused rather than assumed.
- [x] 3.4 Make replay of the same request ID report the recorded outcome without dispatching a second close. A replayed id answers its own record through the request lane, and a fresh id against an already-removed container is refused by name.

## 4. Per-pane reload

- [x] 4.1 Reload one pane slot from its recorded recipe: stop the pane's managed process through the common verified-stop path, require verified exit, then re-run the recipe in that same slot through the backend. Delivered as `topology.reload` (`topology.reload.v1`, requiring `mux.launch` and `mux.exit_observation`): it requires a typed retained exit the backend reports now, then runs the recorded recipe again in the same pane. It does not signal a live process — a command that is still running, or whose exit cannot be established, is refused with the stop-then-reload sequence named, matching how deletion treats a live worker.
- [x] 4.2 Refuse reload for a live process, a missing or stale binding, and a container with no recorded recipe, and require a fresh operator-supplied recipe for an observed container instead of inventing one. Every refusal is recorded on the reload's own request and names what is missing: not a pane, not Radar-created, no binding, no verified serving instance, no recipe held, or a recipe record whose private file is gone.
- [x] 4.3 Keep reload distinct from restart: reload reuses the slot and records its own outcome, restart launches a replacement into a fresh pane, and neither reports a Pi session or assignment outcome it did not establish. A reload changes no container record and answers with the container it acted on, unchanged.
- [x] 4.4 A creation's recipe. `topology.create` accepts an optional recipe for a pane creation only, preflights it against the backend before anything is created, holds it in the private store before the record that says so, runs it in the created pane with no spawn token, and reports only that a recipe is held.

## 5. TUI control plane

- [x] 5.1 Build the tree from containers: group by logical workspace, nest tabs and pane slots, and show the backend binding, registry facts, execution and assignment facets with freshness, and unresolved containers honestly.
      Status: partial, and deliberately so: a workspace or pane row now carries the container Radar records for its place (`tree::ContainerRef`: durable id, kind, provenance, handle, whether a recipe is held, and any source-labelled reason the binding is unresolved), the details panel shows that identity beside the location, and a removed container is offered as no row's identity. Still open: roots and nesting driven by containers rather than by the backend's own groups, a tab row (the tree has none, so no tab container is selectable), and unresolved containers shown as rows of their own rather than as a detail line.
      Superseded detail of the earlier partial state: Containers now reach the client and name the tree. The dashboard client reads them with the registry facts (`topology.list`, gated on the contract, so a daemon that does not serve it reads as no containers rather than failing the refresh), the collector carries them on the observation surface, and the tree titles a workspace or tab group from the container that binds that handle, falling back to the backend's own label. A container the daemon removed names nothing. Still open: rows carrying the container identity and binding (which 5.2's targets need), roots and nesting driven by containers rather than by the backend's own groups, and unresolved containers shown as such.
- [x] 5.2 Add the create, delete, reload, focus and attach actions with the same confirmation discipline as existing lifecycle actions: nothing submitted while opening confirmation, frozen target, explicit confirm. `a` (add), `D` (delete) and `R` (reload) open the same dialog as the lifecycle actions, frozen at the moment it opens: the container id, its place and that place's occupant. The dialog is modal, Cancel is the default, and Confirm revalidates against the latest current observation — a container removed, rebound to another place, or a place whose occupant changed refuses here with nothing sent. Focus is `Enter` on the row as before, and the daemon's own controls are the target rather than an owner file. Still open: a recipe input field (the TUI creates an empty slot), and tab-level create/delete (the tree has no tab row).
- [x] 5.2b Dispatch through the daemon's own controls, off the UI thread. `control_plane::client::ContainerControls` is implemented by the dashboard client over the same socket and handshake as its reads, one control runs at a time, and a control the daemon does not advertise is refused before it is sent. A run with no daemon dispatches nothing and says so.
- [x] 5.3 Read every confirmed container operation back by request ID, keep a lost answer unresolved, and never fall back to the owner-file transport, a local retry or optimistic row removal. The request id is minted at Confirm, carried in the request, and kept in the outcome line the footer shows, so an answer that never arrived leaves an operation to read back. Nothing is removed from the tree optimistically: the next observation is what changes it.
- [x] 5.4 Show observed-external containers as unmanaged with the existing generic close safeguards, and never reload them or record them as owned. The details panel states provenance as created by radar or observed, a reload of a container Radar did not create refuses (no recipe is held for a place it did not make), and a deletion of one still runs the generic close's containment and identity gate.
