# Design

## Decisions

1. **One clean break, no aliases.** Herdsman is the only consumer and has not deployed. A compatibility window would keep Herdr-era names alive in the new contract, which is the thing being removed. The protocol version is the guard: a v1 client gets a typed refusal naming the supported version.
2. **Namespaces follow ownership.** `mux.*` is the physical backend (reads and operations alike; a read is still a mux call), `agent.*` the registry, `spawn.*` managed children, `events.*` the journal, `daemon.*` the process. `child.close` becomes `spawn.close` because it acts on a spawn edge. `request`/`requests` become `mux.request.get`/`.list` because they read mux operation records.
3. **Capability = contract, not method.** Backend capabilities are the backend's declaration under `mux.`. Daemon capabilities name a versioned contract and are derived once, in one place, from what they need (`spawn.v1` needs `mux.create` and `mux.launch`; `spawn.close.v1` needs `mux.close`; `spawn.exit_observation.v1` needs the backend's exit capability). Hand-pushed flags are removed so advertising and serving cannot drift.
4. **Event cursor is the resume position.** `cursor` is what a consumer passes next. `tail` and `more` are information. The bug existed because one word meant two things.
5. **Honest backend identity.** The placeholder `runtime` hid whether a daemon was Herdr or tmux. Registrations and fixtures that carry a location `backend` use the same identity so a dashboard join on backend-qualified location is meaningful.
6. **Dead-pane close is proof-based.** The live-occupant gate protects a live process that may not be ours. A pane reported dead for an edge with its own recorded exit has no occupant to protect, so closing it is safe. Two things can rot between the exit and the cleanup: the pane can be respawned, and the server can be restarted under the same name, which hands the same pane ids to panes that were never ours — so history and a pane id are both insufficient. The gate therefore requires the pane to be dead *now*, the recorded exit to belong to this edge's pane, and the birth identity of the process that served the create to be the one serving now: the verified pid, boot id and start ticks of the backend's own serving process. That identity is a claim the backend makes and the daemon verifies before it records or compares one. The reading of the backend's serving process and the verification of that pid run on the daemon-wide verification budget, so a stalled backend or verifier is abandoned at the deadline and leaves the edge unfenced rather than holding the worker answering a caller. An edge that records none can never be fenced, so it refuses cleanup rather than infer a generation. The result carries the exit the edge recorded — the durable fact a replay repeats — rather than the code read at close time, which a same-UID respawn can change.
7. **Outcome vocabulary.** The audit aligns outcome words (`completed`, `refused`, `unknown`, plus `already_exited` for close) and error codes across operations, with the table recorded in `docs/control-plane.md`. What it found: no word needed renaming. Each carries one meaning, and the useful distinction between a durable request `state` (`pending`, `claimed`, `started`, `completed`) and what the operation did (`outcome`) is kept as two fields rather than collapsed into one word. A *record's* `category: backend_unavailable` stays a diagnostic label beside an `outcome` that carries the certainty, so the record lane needs no new word.
8. **Dispatch uncertainty has its own code.** The audit found one certainty defect: a managed close that may have dispatched was answered `backend_unavailable`, the code this client and any code-switching consumer reads as "nothing was dispatched", so a possibly closed pane could be retried. The user decided the fix belongs inside this break rather than a later change. `outcome_unknown` is a new typed code meaning "dispatched, result not confirmed"; `spawn.close` answers it for the `unknown` outcome, and the client maps it to its unknown certainty and never to a refusal. `backend_unavailable` keeps only its undispatched meaning — no backend wired, a capability absent, or a read-only method's evidence unanswered — and the rejected alternative was to keep documenting the overload, which leaves every consumer free to misread a maybe-effect as no effect. Recording an effect's outcome can still fail after dispatch: that answers `internal`, which is also unknown certainty, and leaves the admitted close record at `unknown`, so a replay reads uncertainty instead of an asserted non-dispatch.

## Risks

- A breaking rename touches every fixture, doc and the client. The fixture validator's full-comparison rule catches stale names. Mitigated by doing the rename as one mechanical task with the validator as the gate.
- The retained-pane close adds a path that closes without the foreground gate. Mitigated by the dead-now requirement, the recorded edge exit, the serving-process generation fence, and explicit respawn and server-restart regressions.
- A backend that cannot name its serving process records no instance, so its panes can never be cleaned up once dead. That is the deliberate direction of failure: a missed cleanup is recoverable by an operator, a wrong close is not.
