# Design

## Context

See `proposal.md` for the motivation and scope. The current ping payload is assembled with `json!` in the server; facts and spawn-exit observations already have Serde DTOs. `pi-radar` has handwritten TypeScript shapes for these. The TypeScript package currently checks facts counts with `Number.isSafeInteger`, while Rust accepts `u64` counts up to its domain invariant; this permits values that JavaScript cannot represent exactly.

## Goals / Non-Goals

**Goals:**

- Make the selected wire shapes derive from the actual Rust DTOs and Serde attributes.
- Publish independent schemas for accepted input and emitted output.
- Generate SDK declarations from those schemas and verify drift reproducibly.
- Constrain only selected facts integers to the exact JavaScript integer range; document rather than re-encode unrelated persistent counters.

**Non-Goals:**

- Replace the JSON-RPC method dispatch or type every method in this first slice.
- Export internal store and lifecycle records.
- Turn JSON Schema into an authority for Rust cross-field or lifecycle validation.
- Change generation, sequence, event-cursor, or operation-record integer wire encodings.

## Decisions

### 1. Export explicit public DTOs, not arbitrary Serde types

Add a small public-contract module for the ping result and task-lane status, and derive `JsonSchema` on those plus the existing public facts and spawn-exit DTOs. The server constructs the ping result through that DTO, so the generated schema cannot drift from the emitted field set. Keep contract names as strings because daemon consumers must tolerate future contract names.

Alternative: derive schemas for every Serde type. Rejected because internal persistence and private protocol models would become accidental public API.

### 2. Generate serialize and deserialize roots separately

Use Schemars `SchemaSettings::draft2020_12()` with `for_serialize()` and `for_deserialize()` for each DTO. Emit deterministic, checked-in JSON schemas under `schema/public/v1/`. Serde attributes remain the source of omission, nullability, defaults, and tagged-union shape.

Alternative: hand-maintain schemas or use one schema per type. Rejected because manual schema copies recreate the drift this change addresses, and one schema cannot always represent both Serde directions.

### 3. Constrain only JavaScript-exposed facts integers

`ContextWindow.tokens`, `ContextWindow.window`, and `background_started_unix_ms` remain JSON numbers, but their accepted maximum is `Number.MAX_SAFE_INTEGER`. Encode the same maximum in the generated schema and a Rust validation constant; a focused test compares the schema constraint to that constant. Keep `window > 0` and `tokens <= window` in Rust domain validation rather than duplicating them as schema validation rules. `u32` protocol/revision and `i32` process exit values remain numbers without conversion. Other 64-bit generations and cursors remain unchanged and are recorded as a separate future wire-compatibility decision.

Alternative: convert all `u64` values to strings. Rejected because it would be a broad breaking wire migration unrelated to the selected DTOs.

### 4. Generate TypeScript only from the selected schema artifacts

Pin `json-schema-to-typescript` as a package development dependency and a TypeScript compiler for the generated declarations. Generate `pi-radar/extension/generated-contracts.ts` from the directions the SDK consumes: ping output, facts input and spawn-exit output. The complementary directional JSON Schemas remain published for other language consumers. Keep its hand-written decoders and Rust domain validation. The test suite typechecks the generated file and checks representative fixtures, including optional fields and both tagged-union cases.

Alternative: Specta. Rejected for this slice because it requires phase-specific Serde export handling and refuses `u64` TypeScript mappings without an explicit precision policy. Alternative: emit TypeScript by hand from schema metadata. Rejected because that would add a second generator to maintain.

### 5. Provide one deterministic generate/check command

A Rust exporter writes schemas from DTOs. A Node script invokes that exporter and the TS generator, either updating checked-in files or comparing generated bytes in check mode. `pi-radar` exposes `generate:contracts` and `check:contracts`; the package test gate runs the check. No runtime dependency is added.

## Risks / Trade-offs

- [Serde behavior and Schemars direction settings may not cover every serializer edge case] → Test actual serialized fixtures against output schemas and ensure schema changes are reviewed with canonical fixtures.
- [Generator upgrades can cause noisy diffs] → Pin tool versions and make regeneration deterministic; update versions in a deliberate change.
- [The safe-integer cap narrows accepted facts values] → Existing Pi/JavaScript publishers already require safe integers; preserve prior accepted snapshots on refusal and document the bound.
- [The selected subset does not eliminate all duplicate wire types] → Keep the scope explicit; expand only when another SDK surface consumes the generated contracts.

## Migration Plan

1. Add Schemars and the public DTO/exporter; generate directional JSON Schemas.
2. Add pinned TypeScript generation and use its declarations in the selected SDK types.
3. Run package, Rust, OpenSpec and Nix gates; review generated schemas and TypeScript output.

Rollback is removal of the exporter, generated artifacts and package generation hooks. The wire changes are limited to rejecting out-of-safe-range facts values; no integer encoding changes are made.

## Open Questions

None for this slice. A future review should decide if long-lived generation/sequence/event-cursor counters need a decimal-string encoding before they approach JavaScript's safe range.
