An attached view draws the projection even when it is empty (an empty canonical tree used to resurrect locally remembered rows, with a regression). `projected()` joins through one index over the local tree and derives every connector in two linear passes instead of searching per row. The subscription socket is registered for cancellation before the handshake, so a stop or re-attach ends a stalled attempt instead of waiting out its reply timeout. A deletion's held-target correlation is recorded when its effect reaches dispatch, not when the question is asked, and a dispatch the scheduler refused retires it. `host_accepted` and the acknowledgement action were deleted: published, never read. The join was measured at 720 rows (24 workspaces x 30 panes, release build, old and new implementations interleaved in one run). Measuring it corrected two claims. The first probe built the projection with an *empty local tree*, so the old per-row search found nothing and cost little while the new code allocated a HashMap unconditionally: the rewrite measured 8% slower (new 112.6 us vs old 104.5 us median). A view that has observed nothing now takes the structure-only path without building an index, and the same comparison then put new at 88.2 us against old at 149.5 us. The old figure itself moved between runs (104.5 -> 149.5), so cross-run numbers are noise and only the within-run ratio means anything. The case the review was worried about — a populated local tree, where a per-row recursive search is genuinely quadratic — is still unmeasured; the rewrite therefore stands on shape, not on a demonstrated gain, and the measurement that matters for the user is the input-to-render tail in 2.8.

The attach loop is free to lose and reclaim a subscription between those two reads, so the assertion raced a legitimate transition. The wait is now for the published state alone, which cannot be the dead session's: every attach attempt clears the mirror before it attaches. A second wrong assertion replaced the first before this settled: publication `update_id`s belong to one daemon's counter and every attach starts a fresh one, so they are not comparable across a restart. ## Audit disposition (2026-10-27)

Fixed, with one item taken as its own slice: the canonical projection now drives rendering (4.6), after the rest of this pass.

Fixed: the forced-deletion correlation used two identities (the frozen plan's request id and a freshly minted one) and settled on acceptance instead of the verdict; the answer now runs under the frozen id and the held key settles only on completed/refused/unknown, with regressions for both halves. `deletion_held` and `holds_deletion` in `App` were dead residue of the frontend-owned lifecycle and are deleted. `SessionLink.adopted` duplicated the mirror's own state and is deleted; the re-take reads the mirror. `Blocking.claimed` repeated `presenter.is_some()` and is deleted. `Confirm.answered` was never set, so a republication could re-ask a question already answered: it is now set on submission, carried across republication, and swallows keys until the session reports the interaction settled. A view's local filter-editing mode is reconciled against the published editor owner whenever nothing of its own is in flight. The duplicated host-action matches in `main.rs` are one executor.

Deferred, with reasons:

- Connection-capacity classes: every connection consumes the global budget before its request type is known, so long-lived subscriptions can crowd out control traffic. Real but only under load; class-aware admission is a transport change.
- Delivering a new publication while the frontend has actions in flight. Today a pending action suppresses adoption of *all* state, so a gate opened elsewhere is seen late. Measured IPC latency makes this invisible at present; it needs a backlog test first, as the audit says.
- An explicit oversized-publication outcome against the 1 MiB framing bound. Not reachable at any plausible fleet size today; the test and the typed refusal belong with the protocol's completion, not before.
- `Blocking.host_accepted` is recorded and drives no transition. Kept because the design distinguishes host acceptance from presenter claim and the popup path reports it; if it is still unused once the UX change reads it, delete both the field and the action.
- Comment volume: the safety invariants stay; getters and fields whose names already say it do not need a paragraph. Trim as files are touched rather than in one sweep.
- The actor's run loop holds input application, effect settlement, attachment/interaction expiry and publication in one function. Each part is individually justified and the audit only proposed extracting them within the module; it is a readability change with no behavioural content, so it is cheaper to do when a change already touches those paths than as a standalone rewrite of a working loop.
- `Session::project()` rebuilds and hashes the row projection even when only the selection changed, and `Navigation::visible_rows` rebuilds its list. Measured at 720 rows: 3.29 ms per projection rebuild, 0.28 ms per navigation step in release. That is not user-visible, and the first fix if it becomes so is a cache invalidated by tree/order/filter/fold state, not a delta protocol. Rewriting the projection path on a guess would trade a known cost for an unmeasured one.

### Open: a settled lifecycle request replayed after a crash

`a_revocation_survives_a_crash_without_a_clean_shutdown` failed once in roughly twenty loaded runs, asserting that replaying the same request id returns the recorded answer. The replayed record was

```
"state": "completed", "outcome": "unknown",
"message": "managed scope membership is unresolved",
"effects": ["launch revoked", "pane kept: the launch's process is not verified gone; …"]
```

where the first answer had been `outcome: "completed"`. `write_settled` writes the record before replying, so a settled request should replay byte-identical. Not fixed, not diagnosed: either recovery rewrites a settled record, or completion is stored under a different key than admission and replay re-derives. The next step is a test that kills after the reply over one request id and asserts replay identity, then the fix. It is not a test-timing defect and must not be papered over with a retry.

### Coverage gaps, classified

- **Through-daemon forced deletion (5.9)** — test-only. The mechanism and both halves exist; only the wiring line is inspection-only, and a session tree with a recorded container would close it without a live process.
- **Competing filter editors** — test-only. The session already enforces one editor owner and a refusal for the second; nothing exercises it across two attachments.
- **Stalled subscription handshake** — test-only. The timeout and the pre-handshake cancellation exist; the test needs a peer that accepts and stays silent.
- **Multi-key sequences (1.2)** — missing logic, not a test gap. There is no pending-sequence buffer, no timeout, no Escape-clears-pending rule and no clearing on gate change anywhere in the app; `tui-actions` supplies the grammar and prefix queries only. This waits on a product decision to add the first multi-key binding.
- **End-to-end latency (2.8)** — measurement only. Push delivery, event-driven wakeups and coalescing exist; nobody has timed input-to-render over the socket under load.
- **Oversized publications** — missing logic. No bound is applied to a subscription frame and there is no typed outcome for exceeding one; a huge tree would fail the write and read as a dropped subscription. Needs a protocol decision and evidence that a plausible fleet can exceed the frame size, so it stays deferred.
- **Class-aware connection admission** — missing logic. Every connection takes the shared 32-connection budget before its type is known, so long-lived UI subscriptions can starve control or presence connections. Deferred pending evidence from acceptance.
- **`sidebar-mode` -> `sidebar-view` sync** — process, not code: the prerequisite for archiving this change.
